# โจทย์ที่ยังรอคำตอบ — สำหรับ AI ที่อยากเข้ามาช่วย

เจ้าของแอปต้องการคำแนะนำในหัวข้อเหล่านี้ **เรียงตามความสำคัญ**
ทุกข้อด้านล่างมีข้อมูลประกอบอยู่ใน repo แล้ว (ดู `app/index.json` → `app/tables/<โดเมน>/<ลำดับ>.json`)

เลือกหัวข้อที่คุณถนัดที่สุด → เปิด issue ด้วยฟอร์ม **AI finding** → ส่งผลเป็นไฟล์ใน `analysis/findings/`

---

## P0 — ความเสี่ยงสูง แก้ก่อน

### 1) ตาราง 6 ตารางที่ไม่มี Security filter
`ข้อมูลงานRT` · `ข้อมูลงานRW` · `FILTER` · `ข้อมูลชื่องานต้นทางปลายทาง` ·
`สรุป_Shipment` · `สรุป_เจ้าของสินค้า`
→ ทุกผู้ใช้ (USER) เห็นและแก้ไขได้ทุกแถว
**อยากรู้:** ควรใช้ Security filter รูปแบบไหนให้เข้ากับโครงสร้างของแอปนี้
(สิทธิ์จริงมีอะไรบ้าง: ADMIN / ผู้ขับ / ผู้อนุมัติ / ฝ่ายคลัง) และควรเปิดเฉพาะคอลัมน์ที่จำเป็นจริงหรือไม่

### 2) `Email พนักงาน` แก้ได้ แต่ถูกใช้เป็น Security filter
คอลัมน์อีเมลที่ใช้เป็นตัวระบุตัวตนถูกตั้ง Read-Only = No
→ ผู้ใช้แก้อีเมลของตัวเองได้ แล้ว Security filter จะเปลี่ยนตาม
**อยากรู้:** ควรย้ายไปใช้ USEREMAIL() แทน หรือควรล็อกคอลัมน์นี้เป็น Read-Only
และกรณีไหนที่ต้องให้พนักงานแก้อีเมลเอง (เช่น เปลี่ยนเมื่อเปลี่ยนชื่อบัญชี)

### 3) สูตรที่อ้างคอลัมน์ที่ไม่มีอยู่จริง (15 จุด ยืนยันแล้วจาก PDF)
ตัวอย่าง: `แจ้งปัญหาระหว่างวัน` อ้าง `[Email พนักงาน]` และ `[DeliveryStatus]` ในขอบเขตที่ไม่มีคอลัมน์เหล่านี้เลย
→ สูตรจะ error
**อยากรู้:** จะแก้โดยอ้างคอลัมน์ของตารางไหนแทน (เจ้าของแอปรู้โครงสร้างที่ถูกต้องมากกว่าเรา)

## P1 — ตรรกะธุรกิจ

### 4) การคิดเงินวางบิล (`D02`)
- `ปริ๊นใบวางบิล.ราคารวม` และ `PDFพนักงาน.ราคารวม` ใช้ `Startdate`/`Enddate` (เคสผิด) → error
- `ข้อมูลการวางบิล.เรทดีเซล` ฝังกฎ "ใช้ราคาวันที่ 25 ของเดือนก่อน" ไว้ในสูตร
- `PriceOverride` ใช้ `ANY(SELECT(...))` ซึ่งดึงค่าบูลีนแทนตัวเลข
**อยากรู้:** โครงสร้างราคา/ส่วนเพิ่มที่ถูกต้องควรเป็นอย่างไร และควรย้ายกฎทางธุรกิจไปไว้ที่ไหนแทนการฝังในสูตร

### 5) บอท 30 ตัว (`D11`)
โครงสร้าง: บอทแต่ละตัวมี `Process for … Process Table` + `… Output` และถูกเรียกจาก
แอคชันชนิด SET_COLUMN_VALUE ที่ตั้ง `ชื่องาน` + `ปริ๊นใบวางบิลแยกตามชื่องาน = TRUE`
**อยากรู้:**
- บอทไหนซ้ำซ้อน / แก้กันเอง (race condition)
- จุดที่ error แล้วค้างเป็น TRUE แล้วเรียกบอทซ้ำ
- ลำดับการทำงานที่ควรเป็น และจุดที่ควรมี idempotency

### 6) ตารางบอทกับตารางจริง 30 ตาราง
ตารางจริง 30 ตาราง ↔ บอท 30 ตัว ↔ ตาราง Process/Output 60 ตาราง
**อยากรู้:** แผนที่แสดงว่าข้อมูลไหลจากตารางไหน → ไหน → ไหน (และจุดที่ข้อมูลหลุดหรือซ้ำ)

## P2 — ความทนทานและประสิทธิภาพ

### 7) สูตรยาวและซ้อนกันลึก
มีสูตรยาว ~1,087 ตัวอักษร ซ้อนกัน 10 ชั้น (เช่น `เรทดีเซล` ใน `ทำเบิกส่วนต่างScgวังน้อย`)
**อยากรู้:** ควรแตกเป็นคอลัมน์ช่วยกี่ตัว อะไรคือจุดที่ควรแยกออกมาก่อน

### 8) Initial value ที่คำนวณค้าง
หลายคอลัมน์ตั้ง `Initial value` ให้ดึงข้อมูลจากตารางอื่น (เช่น `=[SM_Link].[รหัสลูกค้า]`)
→ คำนวณรอบเดียวตอนสร้างแถว แล้วค้างค่าเดิม
**อยากรู้:** จุดไหนที่ "ค้าง" แล้วทำให้เกิดผลผิดจริงบ้าง (เช่นราคา/สถานะที่เปลี่ยนทีหลัง)

### 9) ชื่อคอลัมน์ไม่สม่ำเสมอระหว่างตาราง
`Shipment No` ↔ `ShipmentNo` · `Plan Delivery` ↔ `PlanDelivery` · `Lat / Long` ↔ `Lat/Long`
**อยากรู้:** ควรยึดแบบไหนเป็นมาตรฐาน และต้องแก้กี่จุด (ประเมินความเสี่ยงของการเปลี่ยนชื่อคอลัมน์ของแอปที่ใช้งานอยู่)

## P3 — ประสบการณ์ใช้งาน

### 10) `Valid_If` ที่คืนค่าเป็นรายการ (list) แทนค่าตรรกะ
เช่น `แจ้งปัญหาระหว่างวัน.Shipment No` ใช้ `SM_Today_User[Shipment No] + SELECT(...)`
→ ใช้เป็นเงื่อนไขตรวจความถูกต้องไม่ได้
**อยากรู้:** รูปแบบ Valid_If ที่ถูกต้องสำหรับ "ต้องเป็นแถวที่ยังรับงานได้"

### 11) ช่องกรอกที่ซ่อนตามเงื่อนไขเดียว
`Show_If = ISNOTBLANK([คอลัมน์])` ทำให้ฟอร์มหายทั้งก้อนเมื่อคอลัมน์นั้นว่าง
**อยากรู้:** ควรอิงกับหลายคอลัมน์หรือมีทางเลือกอื่นที่ดีกว่า

### 12) ความสม่ำเสมอของข้อความและรูปแบบ
ข้อความแจ้งเตือนมีทั้งแบบพิมพ์ด้วยมือ (`=มีการเข้าซ่อม`) และแบบเลือกได้
ค่าคงที่ตัวเลขฝังในสูตรหลายจุด
**อยากรู้:** จะทำให้ข้อความและกติกาสอดคล้องกันทั้งระบบอย่างไร

## วิธีทำงานที่แนะนำ

1. เลือกหัวข้อ → อ่าน `docs/data-model.md` แล้วเปิดเฉพาะไฟล์ตารางที่เกี่ยว
2. อ่าน `analysis/analysis/findings/000-baseline-quality.json` ก่อน — มีอะไรเจอแล้วบ้าง (อย่าวิเคราะห์ซ้ำ)
3. ทำงาน → เขียน `analysis/findings/<agent>-<task>.json`
4. รัน `python3 scripts/validate_findings.py analysis/findings/<ไฟล์ของคุณ>.json`
5. เปิด PR พร้อมไฟล์ที่ผ่านการตรวจ

## สิ่งที่จะได้รับคำชมบอก

- ข้อค้นพบที่ **ยืนยันได้** (มีหลักฐาน + หน้า PDF + falsifiable test) → รวมเข้า baseline
- ข้อค้นพบที่ **ช่วยตัดสินใจทางธุรกิจ** (เช่น โครงสร้างราคาควรเป็นอย่างไร) → ส่งให้เจ้าของแอปตัดสินใจ
