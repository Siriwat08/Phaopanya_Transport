# 🖥️ คู่มือ Views · Actions · Slices · Format Rules ครบทุกไฟล์

> วิเคราะห์และคู่มือแก้ไข: **Views 115 รายการ · Actions 214 รายการ · Slices 8 · Format Rules 11**

## 🧒 อ่านก่อน! คำ 4 คำในไฟล์นี้คืออะไร (อธิบายง่ายมาก)

- **View (หน้าจอ)** = ป้ายบอกทาง — คือหน้าจอที่จัดข้อมูลให้ดูแบบไหน (ตาราง / แผนที่ / ฟอร์มกรอก) แอปคุณมี 115 ป้าย
- **Action (ปุ่มสั่งงาน)** = สวิตช์หลายดวงในปุ่มเดียว — กดทีเดียวงานเกิดต่อกันจบชุด แอปคุณมี 214 ปุ่ม
- **Slice (ข้อมูลผ่านกระชอน)** = กระชอนคัดข้อมูล — เหลือเฉพาะแถวที่อยากโชว์ในหน้านั้น แอปคุณมี 8 กระชอน
- **Format Rule (กฎทาสี)** = ธงสีปักแถวข้อมูล — เมื่อแถวเข้าเงื่อนไขจะเปลี่ยนสีให้เห็นไกล ๆ แอปคุณมี 11 ธง

> 🧒 คำไหนยังงง เปิดพจนานุกรมเต็มใน [33-คู่มืออธิบายง่ายมาก-อ่านไฟล์นี้ก่อน.md](33-คู่มืออธิบายง่ายมาก-อ่านไฟล์นี้ก่อน.md)

## 🗺️ ทางเข้าแก้ไขส่วนนี้ใน AppSheet Editor
1. **Views** → คลิกแท็บ **Views** ที่แถบซ้าย → คลิกชื่อวิวที่ต้องการแก้ (หรือคลิกบนหน้าจอตัวอย่างมือถือด้านขวา)
2. **Actions** → คลิกแท็บ **Data** ▸ กลุ่ม **Actions** หรือแท็บ **Actions** (ตามเวอร์ชัน Editor)
3. **Slices** → แท็บ **Data** ▸ กลุ่ม **Slices** ▸ คลิกไอคอนดินสอ
4. **Format Rules** → แท็บ **UX** ▸ กลุ่ม **Format Rules** ▸ คลิกไอคอนดินสอ
5. แก้แล้วกด **Save** ที่แถบบนขวาเสมอ และทดสอบบนหน้าจอตัวอย่างทันที (Preview)

## 1️⃣ Views ทั้งหมด (115 รายการ)

**สถิติตามชนิดวิว:** detail = 38 · form = 36 · table = 32 · deck = 8 · gallery = 1

**การควบคุมการมองเห็น:** มี Show_If อิงบทบาท (USERROLE) = 5 วิว · ไม่มี Show_If = 109 วิว

**แนวทางที่ดี (Best practice) ของ Views:**
- วิวที่แสดงข้อมูลทุกคน (เช่น หน้าหลัก) ควรมี Show_If ควบคุมตามบทบาท: `=OR(USERROLE()="ADMIN", <เงื่อนไขเจ้าของข้อมูล>)`
- วิวแบบตาราง (table) ที่มีข้อมูลเงิน ควรตั้ง Quick Edit เป็น OFF หากกลัวแก้ผิดจากหน้ารวม
- ใช้ GroupBy/SortBy ใน View configuration ช่วยให้ผู้ใช้หาข้อมูลเจอเร็ว (แอปนี้ทำไว้ดีอยู่แล้ว เช่น กลุ่มเดือน/สถานะอนุมัติ)
- ชื่อวิวใช้อีโมจินำหน้าได้เพื่อจำง่าย — แอปนี้ทำแล้ว เช่น 📦 🧾 ✅

## 2️⃣ Actions ทั้งหมด (214 รายการ)

**สถิติตามชนิด Action:** SET_COLUMN_VALUE = 49 · ADD_RECORD = 29 · EDIT_RECORD = 29 · DELETE_RECORD = 29 · NAVIGATE_APP = 29 · EXPORT_VIEW = 21 · EMAIL = 12 · REF_ACTION = 4 · NAVIGATE_DIFFERENT_APP = 3 · COMPOSITE = 3 · NAVIGATE_URL = 3 · ADD_RECORD_TO = 1 · CALL = 1 · SMS = 1

**แนวทางที่ดีของ Actions:**
- Action ลบ (DELETE_RECORD) ควรเปิด "Needs confirmation" เสมอ และตั้ง Conditions ให้เห็นเฉพาะ ADMIN
- Action ชนิด SET_COLUMN_VALUE ที่ใช้เรียกบอท ควรเซ็ตค่าแฟล็กเป็น TRUE/FALSE จริง (ไม่ใช่ข้อความว่าง)
- Action ที่แก้หลายคอลัมน์พร้อมกัน ตรวจชื่อคอลัมน์ใน Assignments ให้ตรงเป๊ะทุกตัว (รวมวรรคและตัวพิมพ์)
- ใช้ "Modifies data" ปิดบนวิวที่เป็นแค่การดู กันผู้ใช้กดสับสน

- **ต้องยืนยันในแอป — Action `อนุมัติ` (พื้นฐาน):** แอคชันเขียนคอลัมน์ `สถานะการ อนุมัติ` ซึ่งต่างจาก `สถานะการอนุมัติ` เฉพาะช่องว่าง — ต้องยืนยันในตัวแอปว่าชื่อจริงเป็นแบบไหน → เปิดในตัวแอปตรวจชื่อคอลัมน์ที่แอคชันเขียน แล้วแก้ให้ตรงทุกตัวอักษร
- **เสี่ยง — Action `อนุมัติ` (พื้นฐาน):** แอคชันอนุมัติไม่มีเงื่อนไขกรองสิทธิ์เลย (condition ว่าง) และเป็น BulkApplicable → ผู้ใช้ที่มีสิทธิ์เห็นแถว (ตาม Security filter คือแถวของตัวเอง รวมถึงผู้ใช้ที่ Login เป็น ADMIN) สามารถกด 'อนุมัติ' ใส่สถานะ 'อนุมัติ' ได้เอง แล้วสูตร 'Email ผู้อนุมัติ' จะบันทึกอีเมลของคนที่กดเป็นผู้อนุมัติ → พนักงานอนุมัติบิลของตัวเองได้ ขัดกับ editable_if ของคอลัมน์สถานะที่กำหนด USERROLE()="ADMIN" (แอคชันไม่ได้ถูกบังคับด้วย editable_if ของคอลัมน์เสมอ) → เพิ่ม condition = USERROLE() = "ADMIN" ให้แอคชัน 'อนุมัติ' (และควรตรวจ [สถานะการ อนุมัติ] <> "อนุมัติ" ด้วย) แล้วปิดการอนุมัติแบบ bulk หรือให้บอท/ผู้บริหารที่มีอีเมลในรายชื่อที่กำหนดเป็นผู้อนุมัติแทน
- **ต้องยืนยันในแอป — Action `รอการอนุมัติ` (พื้นฐาน):** แอคชันเขียนคอลัมน์ `สถานะการ อนุมัติ` ซึ่งต่างจาก `สถานะการอนุมัติ` เฉพาะช่องว่าง — ต้องยืนยันในตัวแอปว่าชื่อจริงเป็นแบบไหน → เปิดในตัวแอปตรวจชื่อคอลัมน์ที่แอคชันเขียน แล้วแก้ให้ตรงทุกตัวอักษร
- **พอใช้ — Action `รอการอนุมัติ` (พื้นฐาน):** แอคชันมีเงื่อนไข ADMIN ถูกต้อง แต่เงื่อนไขเปรียบเทียบกับค่า 'รอการอนุมัติ' ซึ่งไม่ตรงกับค่าจริงที่ระบบเซ็ตให้ (มีเครื่องหมายคำพูด curly ติดท้าย) → เงื่อนไข [สถานะการ อนุมัติ] <> "รอการอนุมัติ" จึงเป็นจริงเสมอ แอคชันจึงปรากฏและทำงานได้แม้แถวนั้นอยู่ระหว่างรอการอนุมัติอยู่แล้ว และ NeedsConfirmation=true แต่ไม่มีข้อความยืนยัน → แก้ค่าเริ่มต้นของคอลัมน์ 'สถานะการ อนุมัติ' ให้เป็นตรง ๆ ก่อน แล้วใส่ ConfirmationMessage ให้ชัดเจนว่า 'ย้อนสถานะเป็นรอการอนุมัติ — ยอดที่อนุมัติแล้วจะถูกยกเลิก'
- **พอใช้ — Action `Delete` (พื้นฐาน):** แอคชันลบแถวไม่มีเงื่อนไขกันการลบแถวที่อนุมัติแล้ว — การป้องกันขึ้นอยู่กับ update mode ของตาราง (USER = ADDS_AND_UPDATES ซึ่งไม่อนุญาตให้ลบ) เท่านั้น ถ้าภายหลังเปลี่ยนเป็น ALL_CHANGES ผู้ใช้ทั่วไปจะลบบิลที่อนุมัติแล้วได้ทันที → ใส่ condition = AND(USERROLE()="ADMIN", [สถานะการอนุมัติ] <> "อนุมัติ") และคง update mode ไว้เป็นชั้นป้องกันที่สอง
- **พอใช้ — Action `ส่งรูปวางบิลหรือสลิปโอนเงิน` (พื้นฐาน):** แอคชันแนะนำไปยังอีกแอปด้วย LINKTOAPP(app_id แบบ hard-code) + LINKTOROW([ID_วางบิล], "ข้อมูลการวางบิล_Detail") และผูกไว้กับคอลัมน์ 'จำนวนด่าน' ที่แสดงเฉพาะเมื่อระบุทางด่วน M-Flow — ถ้าไม่มีแอปปลายทางหรือชื่อ view เปลี่ยน ปุ่มจะพาไปผิดที่ ทั้งที่ยังไม่มีเงื่อนไขป้องกัน → เก็บ app_id ไว้ในคอลัมน์ค่าตั้งของแอป (Settings) และเพิ่ม condition ตรวจว่าแถวมี [รูปถ่ายบิลงาน] แล้วจึงแสดงปุ่ม

- กฎ `แจ้งเตือนราคาหลังวิ่งงาน` ฝังรายชื่องานไว้ในสูตร (`นครหลวง`, `โอนคลัง พว`, `โอนคลัง นำ วิวัฒน์`, ...) — ถ้าเพิ่มชื่องานใหม่ต้องมาแก้สูตรนี้ทุกครั้ง ควรย้ายรายชื่อไปเป็นคอลัมน์ตั้งค่าในตาราง (เช่น คอลัมน์ "เช็คราคา? = Yes" ในตารางชื่องาน) แล้วใช้ `IN([ชื่องาน], SELECT(ตารางชื่องาน[ชื่องาน], [เช็คราคา?]))`
- กฎ `ทำเบิกได้`/`ทำเบิกไม่ได้` ตรวจ `>0` กับ `<0` — ค่า 0 ไม่เข้าเคสใดเลย ควรเติมเงื่อนไข `=0` หรือเปลี่ยนเป็น `>=0` ตามความหมายจริง
- สีควรใช้คู่ที่จำง่าย: เขียว=สำเร็จ เหลือง=รอ เข้ม=ต้องสนใจ และตรวจว่าไม่มีกฎทับซ้อนกัน (ลำดับกฎมีผล: กฎที่อยู่บนจะใช้ก่อน)
