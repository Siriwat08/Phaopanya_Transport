## 1) สรุปผู้บริหาร (Executive Summary)

แอปนี้เป็นระบบงานขนส่งครบวงจรที่สร้างด้วย AppSheet บนฐาน Google Sheet ครอบคลุมตั้งแต่รับงาน จัดเส้นทาง สแกนเอกสาร วางบิล คิดราคา ควบคู่กับระบบบอทอัตโนมัติ 30 ตัว ภาพรวมถือว่า **"ทำงานได้จริงและมีความคิดระบบดีอยู่แล้ว"** — หลายตารางมี Security filter ถูกหลัก มีระบบบทบาท ADMIN/USER ชัดเจน มีการแยกตารางข้อมูลหลักกับตารางรายงาน และระบบประกาศ/รับทราบที่มีลายเซ็นดิจิทัล ซึ่งเป็นโครงสร้างที่แอปธุรกิจจำนวนมากยังไม่มี

อย่างไรก็ตาม การวิเคราะห์เชิงลึกพบจุดที่ต้องดูแล 3 กลุ่มใหญ่:

1. **บั๊กที่ยืนยันแล้ว 27 ข้อ** — สูตรที่อ้างชื่อคอลัมน์ผิดเคส (เช่น `Startdate` ที่จริงต้องเป็น `StartDate`) สูตรที่อ้างคอลัมน์ที่ไม่มีอยู่ในขอบเขตของมัน และสูตรที่ไวยากรณ์ผิด (comma เกิน) — กลุ่มนี้ทำให้ตัวเลขเงินในใบวางบิล/รายงานผิดจริง ต้องแก้ก่อนใคร เวลาลงทุน 1-2 ชั่วโมง
2. **ความเสี่ยงด้านความปลอดภัยและเงิน** — ตาราง 23 ตารางที่ไม่มี Security filter, คอลัมน์อีเมลที่ใช้กรองสิทธิ์ยังแก้ได้โดยผู้ใช้, และตรรกะราคาดีเซลที่ฝังกฎ "วันที่ 25" ไว้ในสูตรยาว ~900 ตัวอักษร — แก้ได้ภายในสัปดาห์เดียว
3. **คุณภาพเชิงระยะยาว** — สูตรยาว/ซ้อนลึก 4 จุด, Enum ไม่มีค่าให้เลือก, ชื่อคอลัมน์ไม่สม่ำเสมอข้ามตาราง (เช่น `Shipment No` vs `ShipmentNo`) — ทยอยแก้ได้เรื่อย ๆ ไม่เร่งร้อน

**คำตอบสำหรับคำถาม "มันจะดีกว่านี้ได้อีกมั้ย": ได้แน่นอน** — แผนปรับปรุง 3 ระยะในหัวข้อที่ 9 ออกแบบให้เริ่มจากอะไรที่กระทบเงินที่สุดก่อน ใช้เวลารวมประมาณ **2-3 สัปดาห์ในเวลาว่าง** โดยไม่ต้องหยุดใช้งานแอป และทุกข้อในแผนมีคู่มือรายตารางพร้อมสูตร copy-paste อยู่ในชุดไฟล์นี้แล้ว

## 4) ผลวิเคราะห์ 6 มิติ

### 4.1 Data Model & Keys

- **ตารางไม่มี Key ชัดเจน 0 ตาราง** (สเปกไม่มีคอลัมน์ Key = Yes): — — ควรเพิ่มคอลัมน์ `ID` ด้วย `UNIQUEID()` ตามคู่มือรายตาราง
- คอลัมน์ Key ที่ยังแก้ไขได้ (Read-Only = No) มีจุดเสี่ยง "แก้คีย์แล้วแถวหาย" — พบในหลายตาราง ดูเช็คลิสต์แต่ละไฟล์
- ชื่อคอลัมน์ไม่สม่ำเสมอข้ามตาราง 3 ชุด: `Lat/Long/Lat·Long`, `Plan Delivery/PlanDelivery`, `Shipment No/ShipmentNo` — เสี่ยงสูตรอ้างผิดเมื่อ copy สูตรข้ามตาราง

### 4.2 Security & ข้อมูลส่วนบุคคล (PDPA)

- **23 ตารางไม่มี Security filter:** Acknowledge_Logs, Announcements, Doc_Return, FILTER, Image_Doc_Return, PDFพนักงาน, PriceOverride, Price_Table, ScanDocs, _Per User Settings, ข้อมูลงานRT, ข้อมูลงานRW, ข้อมูลชื่องานต้นทางปลายทาง, ข้อมูลพนักงาน, ปริ๊นใบวางบิล, ราคาน้ำมันดีเซล, ราคาในระบบก่อนส่งสินค้า, สรุป_Shipment, สรุป_เจ้าของสินค้า, สรุปเบิกส่วนต่าง, สร้างเอกสาร, ส่งงานที่ยังไม่มีข้อมูลในระบบ, หน้าหลัก — ผู้ใช้ทุกคนเห็นข้อมูลทุกแถว รวมชื่อ/เบอร์โทร/ทะเบียนรถ/พิกัด
- **คอลัมน์อีเมลที่ใช้กรองสิทธิ์ยังแก้ได้** ในตารางที่ใช้ `[Email พนักงาน] = USEREMAIL()` เป็นตัวกรอง — ผู้ใช้เปลี่ยนอีเมลในแถวตัวเองแล้วจะเห็นงานคนอื่น
- **คอลัมน์ PII ที่ยังไม่ได้ตั้ง Sensitive data = 62 จุด** — ควรตั้ง Yes ตามคู่มือ (ชื่อ-นามสกุล, เบอร์โทร, อีเมล, ทะเบียนรถ, ที่อยู่, พิกัด GPS, ลายเซ็น)
- **จุดแข็ง:** ตารางวางบิล/งานหลักหลายตารางมี Security filter ถูกหลักแล้ว และใช้ `SWITCH(USERROLE(), ...)` จำกัดสิทธิ์ — นี่คือแนวทางที่ดี ควรขยายให้ครบทุกตาราง

### 4.3 คุณภาพสูตรและตรรกะธุรกิจ

- **บั๊กยืนยันแล้ว 27 ข้อ** (รายละเอียดเต็มในหัวข้อ 5) — เคสผิด 8 · อ้างคอลัมน์ไม่มี 15 · ไวยากรณ์ 4
- **เรทดีเซล** (`ข้อมูลการวางบิล.เรทดีเซล`) สูตรยาว ~900 ตัวอักษร IF ซ้อน 4 ชั้น ฝังกฎ "วันที่ 25 ของเดือนก่อน" และใช้ `ANY(SELECT(PriceOverride[...]))` ที่ถ้ามีหลายแถวทับช่วงวัน จะได้ค่าแถวแรกโดยไม่มีกฎเลือก — ราคาวางบิลไม่คาดเดาได้
- **คีย์เดือน (พ.ศ.)** ถูกเขียนซ้ำ 3 ตาราง 3 แบบ (`&` กับ `CONCATENATE` ปนกัน) ฝังเลข 543/2500 — ควรรวมเป็นคอลัมน์ช่วยกลาง
- **Initial value คำนวณค้าง** หลายจุด: ค่าที่ควรอัปเดตตามสถานะ (เช่น อนุมัติแล้ว/สแกนแล้ว) ถูกคำนวณครั้งเดียวตอนสร้างแถว แล้วค้างค่าเก่า → รายงานผิด

### 4.4 ประสิทธิภาพ

- **สูตรยาว/ซ้อนลึก 2 จุด** — ที่ช้าที่สุดคือ `เรทดีเซล` ใน `ทำเบิกส่วนต่างScgวังน้อย` (ยาว ~1,087 ตัวอักษร ซ้อน 10 ชั้น)
- ตารางบอท 60 ตารางเป็น state table ของระบบ — ยิ่งบอทเขียนบ่อย ยิ่ง sync ช้า; `ปริ๊นใบวางบิลทุกงาน` เป็น COMPOSITE ขนาด 38 ขั้น ควรทบทวนว่ายังจำเป็นหรือตัดได้กี่ขั้น

### 4.5 ระบบบอทและการอัตโนมัติ (D11)

- โครงสร้างมาตรฐาน: Action `SET_COLUMN_VALUE` ตั้ง `ชื่องาน` + `ปริ๊นใบวางบิลแยกตามชื่องาน = TRUE` → บอทต่อชื่องานทำงาน → เขียน Output → ปล่อยแฟล็ก
- **จุดเสี่ยงพบ 20 ข้อ (กลุ่ม BOT):** (1) Action เคลียร์แฟล็กด้วย `=""` (ข้อความว่าง) แทน FALSE — เงื่อนไขบอทที่ตรวจ TRUE เชื่อถือไม่ได้ (2) ถ้าบอท error กลางทาง แฟล็กค้าง TRUE แล้วบอทเรียกซ้ำ (3) Action อ้างคอลัมน์ `ชื่อ งาน` (มีวรรค) ขณะที่สเปกมี `ชื่องาน` — ต้องยืนยันชื่อจริงในแอป
- **คำแนะนำหลัก:** เปลี่ยนการเคลียร์แฟล็กเป็นค่า FALSE จริง และเพิ่มเงื่อนไขบอทให้เริ่มทำงานเฉพาะเมื่อแฟล็ก = TRUE (ไม่ใช่ช่วง transition)

### วิธีแก้แบบกลุ่ม (ทำครั้งเดียวได้หลายข้อ)

**กลุ่ม A — ผิดเคส `Startdate`/`Enddate` (แก้ 4 คอลัมน์ ใน 4 ตาราง):** ปริ๊นใบวางบิล.ราคารวม · PDFพนักงาน.ราคารวม · สร้างเอกสาร.ราคารวม · สร้างเอกสาร.ราคารวมคนขับ — สูตรเดิมใช้ `[_THISROW].[Startdate]` กับ `[_THISROW].[Enddate]` แต่คอลัมน์จริงชื่อ `StartDate`/`EndDate` วิธีแก้: เปิดคอลัมน์ทั้ง 4 → แก้สูตรเป็น

```
=SUM(SELECT(ข้อมูลการวางบิล[ราคา], AND([ชื่องาน] = [_THISROW].[ชื่องาน], [วันที่] >= [_THISROW].[StartDate], [วันที่] <= [_THISROW].[EndDate])))
```

**กลุ่ม B — อ้างคอลัมน์ไม่มีในขอบเขต (15 ข้อ):** ส่วนใหญ่คือ `Valid_If` ของ `Shipment No`/`Invoice No` ใน ตารางแจ้งปัญหาระหว่างวัน + Process/Output ของ Telegram bot ที่อ้าง `[Emailพนักงาน]` / `[Email พนักงาน]` / `[DeliveryStatus]` ใน `ข้อมูลงานRT` (ตารางนี้ไม่มีคอลัมน์เหล่านี้) — วิธีแก้ต้องตัดสินใจ 2 ทาง:

```
# ทาง 1: ถ้าตั้งใจกรองงานของผู้ใช้เอง — อ้างคอลัมน์ที่มีจริงใน ข้อมูลงานRT เช่น
=SELECT(ข้อมูลงานRT[Shipment No], [Email] = USEREMAIL())   # ใช้ชื่อคอลัมน์อีเมลที่มีจริงใน ข้อมูลงานRT
# ทาง 2: ถ้าตั้งใจดึงจากตารางงานประจำวัน (ที่มี DeliveryStatus จริง) — เปลี่ยนตารางเป้าหมาย
=SELECT(ตารางงานประจำวัน[Shipment No], [Email พนักงาน] = USEREMAIL())
```

**กลุ่ม C — ไวยากรณ์ (4 ข้อ):** `ตารางงานประจำวัน.ลำดับแรก` (comma ท้ายใน SELECT) และ `Acknowledge_Logs.ข้อความประกาศ` (สตริงติดกัน + comma ท้าย) — ลบ comma ส่วนเกินและเติม `+` คั่นสตริงตามสูตรแนะนำในคู่มือรายตาราง

## 8) ❓ ต้องยืนยันในแอป (120 ข้อ) — วิธีตรวจเป็นขั้น

กลุ่มนี้ "ไม่ใช่บั๊กที่พิสูจน์แล้ว" — เป็นจุดที่สเปก PDF ยืนยันชื่อคอลัมน์/สูตรไม่ได้ (ปัญหาช่องว่างภาษาไทยใน PDF แยกไม่ออก) ต้องเปิดแอปเทียบจริง วิธีตรวจอย่างเป็นระบบ:

1. เปิด AppSheet Editor → Data → Tables → เลือกตาราง → เทียบชื่อคอลัมน์กับคู่มือรายตาราง (เน้นชื่อที่มีวรรค/ขีดกลาง)
2. ถ้าชื่อในสูตร ≠ ชื่อจริง → แก้สูตรให้ตรง (แบบเดียวกับกลุ่มบั๊กผิดเคส)
3. ถ้าชื่อในคู่มือ "ไม่พบ" ในแอปจริง → บันทึกใน Issue ของ repo ว่าไม่พบ เพื่อปรับฐานข้อมูลให้ตรง
4. ใช้เวลาตรวจวันละ 2-3 ตาราง ไล่ตามลำดับตารางที่มีข้อค้นพบมากสุด: ทำเบิกส่วนต่างScgวังน้อย (104) → ข้อมูลการวางบิล (55) → ปริ๊นใบวางบิล (60) → แจ้งปัญหาระหว่างวัน (65)

| กลุ่ม | จำนวน | วิธีตรวจ |
|---|---|---|
| ต้องยืนยันในแอป | 120 | ดูหัวข้อ 8 วิธีตรวจในแอป |

## 10) 💪 จุดแข็งที่ควรรักษาไว้ (อย่าเปลี่ยน)

1. **ระบบบทบาทชัดเจน** — ใช้ `SWITCH(USERROLE(), "ADMIN", ..., "USER", ..., "READ_ONLY")` กำหนดสิทธิ์ต่อตารางหลายตาราง ซึ่งเป็นแนวทางที่ AppSheet แนะนำ
2. **Security filter บนตารางงานหลัก** — `=OR(USERROLE() = "ADMIN", [Email พนักงาน] = USEREMAIL())` ทำงานถูกหลัก server-side filtering
3. **ระบบประกาศ + รับทราบด้วยลายเซ็น** — Announcements + Acknowledge_Logs มีการจับลงชื่อพนักงาน ระบบประกาศโรงงานสมัยใหม่มักยังไม่ทำถึงระดับนี้
4. **การจัดกลุ่มวิวอย่างมีระบบ** — GroupBy เดือน/สถานะอนุมัติ + SortBy ช่วยให้ผู้อนุมัติหางานเจอเร็ว
5. **เอกสาร/รูปถ่ายครบกระบวนการ** — สแกนต้นทาง-ปลายทาง คืนเอกสารเข้าคลัง พร้อม Image_Doc_Return แยกไฟล์รูป
6. **ระบบบอทแยกงานตามชื่องาน** — โครงสร้าง Process/Output ต่องานชัดเจน (ต้องแก้แค่การเคลียร์แฟล็กตามระยะ 2)
7. **รายงานผู้บริหารบนหน้าหลัก** — วิวสรุป_เจ้าของสินค้า/สรุป_Shipment พร้อม Format Rule เตือนราคาหลังวิ่งงาน

## 11) 🎯 Best Practices สำหรับการพัฒนาต่อไป

1. **กฎธุรกิจห้ามฝังในสูตร** — เลข 543, 2500, วันที่ 25, ค่า 200 และรายชื่องานใน Format Rule ควรอยู่ใน "ตารางตั้งค่า" แล้วดึงด้วย LOOKUP — แก้กฎที่เดียวได้ทั้งระบบ
2. **ตั้งชื่อคอลัมน์แบบเดียวตลอดระบบ** — เลือกไว้ว่าจะใช้มีวรรคหรือไม่ และใช้ตัวพิมพ์ใหญ่-เล็กแบบเดียว (เช่น `ShipmentNo` หรือ `Shipment No` ต้องเลือกอย่างใดอย่างหนึ่งทั้งแอป)
3. **App formula คือค่ามีชีวิต, Initial value คือ snapshot** — ก่อนวางสูตร ถามตัวเองว่า "ค่านี้ต้องอัปเดตตามข้อมูลอื่นไหม" ถ้าใช่ → App formula
4. **ใช้ Ref ให้เป็น** — ความสัมพันธ์ระหว่างตารางควรประกาศผ่านชนิด Ref แทนการเดาชื่อตารางใน SELECT เพื่อให้ได้ dropdown และ REF_ROWS()
5. **บอทต้อง idempotent** — ทุกบอทควรตรวจก่อนทำงานว่า "ผลลัพธ์นี้เขียนไปแล้วหรือยัง" (เช่น เช็ค Output ที่มีแถวเดียวกัน) กันการเรียกซ้ำเมื่อแฟล็กค้าง
6. **แก้ทีละจุด ทดสอบทุกครั้ง** — สำรองสูตรเดิมก่อนแก้ทุกครั้ง แก้จุดเดียว ทดสอบ 5 แถวจริง แล้วค่อยแก้จุดถัดไป
7. **ใช้ repo นี้เป็น "สมุดทะเบียน"** — ทุกครั้งที่แก้แอปแล้ว อัปเดตข้อค้นพบใน `analysis/findings/` ตามรูปแบบของ repo ระบบจะตรวจซ้ำให้อัตโนมัติ

**ความต้องการ:** เมื่อ `ตารางงานประจำวัน.LatLong_Actual` มีข้อมูล ให้แอปตรวจว่า `SCGนครหลวงJWDภูมิภาค.จุดส่งสินค้าปลายทาง` ห่างจากพิกัดจริงไม่เกิน 20 เมตร — ถ้าเกินจะกดบันทึกไม่ได้ แต่มีปุ่ม/สวิตช์ "ยืนยันตำแหน่งถูกต้อง" ให้กดผ่าน พร้อมบันทึกว่า **"มีแก้ไข โดยใคร เมื่อไร"**

**ผลการตรวจโครงสร้างจริง (สรุป):** ทั้ง 2 คอลัมน์เป็น LatLong type พร้อมใช้ ✓ · มี Ref `SM_Link_SCG` เชื่อม 2 ชีตอยู่แล้ว (ดึงพิกัดด้วย `[SM_Link_SCG].[LatLong_Actual]` ไม่ต้องเขียน LOOKUP ใหม่) · `จุดส่งสินค้าปลายทาง` มี Valid_If เดิม (ค่าว่าง/0,0) ที่ต้อง merge · `DISTANCE()` คืนค่ากิโลเมตร (×1000 = เมตร) · AppSheet ไม่รองรับปุ่ม Action ในฟอร์ม จึงออกแบบเป็น "สวิตช์ยืนยันในฟอร์ม (โผล่เฉพาะเกิน 20 ม.) + ปุ่ม Action จริงบนหน้ารายละเอียดสำหรับยืนยันหลังบันทึก"

**สรุปสิ่งที่ต้องเพิ่ม (ในตาราง SCGนครหลวงJWDภูมิภาค เท่านั้น):**

| สิ่งที่เพิ่ม | ชนิด | หน้าที่ |
|---|---|---|
| คอลัมน์เสมือน `ระยะห่างพิกัดจริง_เมตร` | Decimal (Virtual) | คำนวณระยะครั้งเดียว ใช้ซ้ำทุกจุด |
| คอลัมน์ `ยืนยันตำแหน่ง_ด้วยตนเอง` | Yes/No (จริง) | สวิตช์/ปุ่มยืนยันในฟอร์ม (Show เมื่อเกิน 20 ม.) |
| คอลัมน์ `ยืนยันตำแหน่ง_โดย` | Email (จริง) | บันทึกอีเมลผู้ยืนยัน — "โดยคนนี้" |
| คอลัมน์ `ยืนยันตำแหน่ง_เวลา` | DateTime (จริง) | บันทึกเวลาที่ยืนยัน |
| Valid_If ใหม่ (merge กับเดิม) | สูตร | บล็อกบันทึกเมื่อเกิน 20 ม. + ทางผ่านเมื่อยืนยันแล้ว |
| Action `ยืนยันตำแหน่งปลายทางถูกต้อง` | Data set values | ปุ่มยืนยันหลังบันทึก + ข้อความ "มีการยืนยันแก้ไข โดย ... เมื่อ ..." |
| Format Rule แถวสีส้ม | Format Rules | เห็นทันทีว่าแถวนี้มีการยืนยันแก้ไข |
| Bot แจ้งเตือน (เสริม) | Automation | ดันรายงาน "ยืนยันมือ" ไปหาหัวหน้า/Telegram |

**ผลต่อแผนเดิม:** ไม่ต้องรื้อ — เป็นการเพิ่มเข้าไป แผนที่/Map view และแผน 3 ระยะเดิมไม่กระทบ มีจุด merge เดียวคือ Valid_If ของ `จุดส่งสินค้าปลายทาง` (สูตรเต็มพร้อม paste อยู่ในไฟล์ 32 ขั้นที่ 3) — ใช้เวลาทำจริงประมาณ 45-60 นาที
